# MiniSIP

Минимальный SIP-телефон для Android. Без внешних библиотек: SIP, SDP, Digest, RTP и G.711 написаны с нуля.
Нужны только платформа Android и Java 17.

## Структура

```
ru.minisip
├── net     Udp      ← никого не импортирует
├── media   Media    ← net.Udp         (RTP, G.711, микрофон/динамик)
├── sip     Sip      ← net.Udp, media.Media   (REGISTER, INVITE, BYE, CANCEL, Digest, SDP)
├── screen  Screen   ← никого          (датчик приближения)
├── vpn     Vpn      ← никого          (IKEv2-клиент, ESP, tun)
└── app              ← всё сверху      (корень композиции, UI)
```

- В каждом пакете наружу торчит один публичный интерфейс и статическая фабрика `create(...)`.
  Реализации (`UdpImpl`, `MediaImpl`, `SipImpl`, `ScreenImpl`, `VpnImpl`) package-private: снаружи их не видно.
  Единственное исключение — `vpn.TunService`: системный `VpnService` обязан быть public, но его имя стоит только в манифесте.
- Через границы пакетов ходят только встроенные типы (`String`, `int`, `byte[]`, `boolean`) и вложенные
  интерфейсы-колбэки (`Udp.Listener`, `Sip.Listener`). Кастомных структур нет, циклов между пакетами нет.
- `python3 tools/check_imports.py` проверяет это автоматически.

## Датчик приближения (`screen.Screen`)

`Screen.start()` вызывается в начале дозвона, `stop()` — в конце вызова.

- Датчик закрыт → экран гаснет (`PROXIMITY_SCREEN_OFF_WAKE_LOCK`).
- Датчик открыт → экран зажигается, а если он был погашен (например, кнопкой питания), приложение его включает.
- Кнопка питания работает штатно и дублирует управление экраном: гасит и зажигает вручную, датчик при этом остаётся главным.
- После отбоя экран не зажигается, пока телефон у уха.

## VPN (`vpn.Vpn`)

Третий блок на странице: *VPN server*, *VPN login*, *VPN password*, *VPN pre-shared key* (необязательно), *VPN CA certificate* (необязательно),
кнопки **VPN connect** / **VPN disconnect**.
Подключена — активна только disconnect; не подключена — только connect (и ещё connect неактивна во время вызова).

Как это работает:

1. `Vpn.connect()` запускает `TunService` (системный `VpnService`). Он создаёт tun (`Builder.establish()`),
   заодно система вытесняет любой другой действующий VPN. В туннель попадает трафик **этого приложения и выбранных в списке «VPN apps»**
   (`addAllowedApplication` по каждому пакету, маршрутизирует по UID сама Android), остальная система не затронута.
   IPv6 в туннель не умеет: маршрут `::/0` ведёт в «чёрную дыру», приложения откатываются на IPv4. Список применяется при подключении.
2. `Ike` ведёт IKEv2 (RFC 7296) в чистых байтах, `Esp` заворачивает IP-пакеты в ESP (туннельный режим, UDP 4500),
   `Tunnel` перекачивает пакеты tun ⇄ сокет, держит keepalive и DPD. Криптография — `javax.crypto` и `BigInteger`.
3. Когда туннель поднят, `App` вызывает `Udp.bind(iface)` для SIP- и RTP-сокетов: `Network.bindSocket` привязывает их
   к сети tun-интерфейса. Регистрация на АТС переоткрывается через туннель, вызов идёт строго через него.
   Если интерфейс пропал, `open()` возвращает -1: мимо туннеля пакеты не уходят.
4. Туннель не поднят или упал — `Udp.bind(null)`, снова основной стек системы без вмешательства
   (регистрация переоткрывается; идущий вызов завершается).

Два способа входа. Если поле pre-shared key пустое — **логин и пароль** (EAP-MSCHAPv2, как у большинства серверов на strongSwan,
Windows RRAS и т.п.): сервер обязан показать сертификат, клиент проверяет цепочку до доверенного корня (системное хранилище
Android или PEM из поля CA, можно вставить и сам сертификат сервера), имя хоста в SAN (DNS или IP, `*.` в первой метке)
и подпись сервера в AUTH (RSA PKCS#1 v1.5 с SHA-1/256/384/512, ECDSA; RSASSA-PSS не поддерживается), затем MS-CHAPv2 с проверкой
ответа сервера `S=...`, итоговый AUTH считается от MSK. Отзыв сертификатов (CRL/OCSP) не проверяется. Если поле pre-shared key заполнено —
вход по общему ключу, login служит IKE-идентификатором.

Что умеет IKE-клиент: IKE_SA_INIT и IKE_AUTH, DH группа 14,
AES-CBC-128/256 + HMAC-SHA2-256-128 / HMAC-SHA1-96 + PRF SHA-256/SHA-1 или AES-GCM-16-128/256, cookie, запрос адреса и DNS (CP),
один дочерний ESP-канал, окно повторов, DPD, Delete. Идентификатор клиента: с `@` — почта, четыре числа — IPv4, иначе FQDN.
ESP всегда внутри UDP 4500: в NAT-D нарочно отправляется неверный хеш источника, чтобы сервер включил инкапсуляцию
(сырого ESP в приложении нет). Адрес сервера — IPv4.

Правило слоёв здесь то же: на границу выходят только `String`, `int`, `boolean` и `Context`. `Network`, `ParcelFileDescriptor`
и прочее остаются внутри `net` и `vpn`.

## Сборка

Откройте папку в Android Studio (AGP 8.7.3, Gradle 8.9+), либо `gradle assembleDebug` с установленным Android SDK 35.

## Проверки без Android SDK

`sh jvmtest/run.sh` — слои, кодек и RTP, Digest по вектору RFC 2617, привязка сокетов к интерфейсу (`NetTest`),
крипто и ESP (`CryptoTest`: HMAC по RFC 4231, MD4 по RFC 1320, MS-CHAPv2 и ключи MPPE по RFC 2759/3079, подделки, окно повторов),
полный IKEv2-туннель против независимого ответчика `jvmtest/fake_ike.py` (нужен `pip install cryptography`; 22 сценария:
три набора алгоритмов, cookie, неверный ключ, NO_PROPOSAL, молчащий и «умерший» сервер, Delete от сервера, DPD, мусор и подделки;
логин/пароль с настоящими сертификатами: корень → промежуточный → сервер, подпись SHA-256 и SHA-1, закреплённый сертификат,
неверный пароль, чужой и неизвестный CA, чужое имя хоста, поддельная подпись, сервер без доказательства пароля)
и SIP-сценарий против скриптового сервера.
Экран, UI, `VpnService`, `Network.bindSocket` и реальный микрофон проверяются только на устройстве. Ответчик написан мной по тем же RFC,
поэтому со **стороны сервера** сверка идёт по векторам RFC; порядок ключей в MSK и поведение конкретного сервера (strongSwan, Windows) на живом сервере не проверялись.

Известно: SIP-сценарий (`fake_server.py`) падает на входящем вызове ещё до VPN, потому что в приложении входящих нет.

## Ограничения

- UDP без NAT-traversal (STUN/ICE нет). За NAT работает, если сервер отвечает на адрес, откуда пришёл запрос.
- Кодеки: только PCMA и PCMU. DTMF, удержание, перевод, TLS/SRTP нет.
- Digest только с MD5.
- VPN: только IPv4, вход по PSK или EAP-MSCHAPv2 (без клиентских сертификатов и других EAP), только DH 14, без перегенерации ключей (сервер должен ставить большое время жизни SA или переподключаться), нет IPv6 и MOBIKE.
- Входящих нет. Приложение пока что расчитано только на исходящие.
- Все in-dialog запросы уходят на сервер регистрации (или на адрес, откуда пришёл входящий INVITE).
